# deliver-pdf — сдача в PDF

Документ из `spec/` уходит за пределы корпуса: заказчику, в письмо, на
согласование. PDF — единственный экспортный формат ядра; docx осознанно
нет, в Confluence владелец импортирует `.md` сам.

## Команда

```sh
python3 .claude/skills/deliver-pdf/scripts/export_pdf.py spec/<док>.md
# → spec/<док>.pdf ; опции: -o путь, --corpus wiki spec, --engine auto|…|html,
#   --strict (битая ссылка — не сдача), --md/--bundle пакет.md док1.md док2.md
```

Экспортёр детерминированный: `[[wikilink|текст]]` становится текстом,
`![[картинка]]` — встроенным изображением (поиск по basename в корпусе),
frontmatter снимается, `title` из паспорта идёт в заголовок PDF только
если в теле нет своего H1 — иначе заголовок двоился бы. Дальше pandoc и
первый доступный движок:

| Движок | Откуда берётся |
|---|---|
| `typst` | `brew install typst` — рекомендуемый, самый чистый вывод |
| `weasyprint` / `wkhtmltopdf` | если стоят |
| Chrome headless | есть почти на любом маке — работает из коробки |
| standalone-HTML | последний рубеж: файл `.html` + печать в PDF из браузера (⌘P) |

Движок, не ответивший за 180 секунд, считается провалившимся и уступает
очередь следующему: зависший рендерер не должен съедать сдачу.

Корпус по умолчанию — `wiki/`, `spec/`, `assets/` от корня проекта плюс
каталог документа; `--corpus` перекрывает список, `-o` создаёт каталог,
если его нет. Неразрешённые `[[ссылки]]` и `![[embeds]]` экспортёр
перечисляет в stderr и PDF всё равно собирает — останавливает сдачу
`--strict`, с кодом 1. Код 2 — нет документа, нет pandoc, движок не
собрал PDF или явно запрошенного `--engine` в системе нет; код 3 —
PDF-движка нет вовсе и рядом оставлен `.html`. `--engine html` — не
авария, а запрошенный формат: standalone-HTML с кодом 0.

## Перед сдачей — обязательный минимум

1. `link-check` по документу: битые ссылки в сдаваемом ТЗ недопустимы.
2. Гигиена: grep по документу на внутренние IP, хосты и токены (ось
   «гигиена» в `tz-audit`) — leak-guard защищает запись, но не экспорт.
   Отдельно — grep на `{{secret:`: плейсхолдеры экспортёр не
   подставляет, и в PDF они уедут как есть: либо заменяешь их руками на
   значения, которые получателю положено видеть, либо останавливаешь
   сдачу до решения владельца.
3. Вердикт `verifier`: за пределами `stage` он судит по критериям одной
   строкой от автора — кто читатель и что должно выполняться. Сдаётся
   документ со `status: review` или `approved`, черновики не
   экспортируются.

## Пакет для NotebookLM

NotebookLM у владельца — инструмент объяснения для людей: loft пишет,
NotebookLM учит. Связь односторонняя и без сервисов между ними.

Грузить можно PDF из этого скилла или сам markdown — его готовит
`--md пакет.md`: снимает паспорт-frontmatter (получателю он не
адресован) и разворачивает `[[wikilinks]]` в текст, иначе NotebookLM
читает чужой синтаксис как мусор. У ноутбука есть лимит источников,
поэтому пакет собирается по домену корпуса, а не по странице:
`--bundle пакет.md spec/домен/*.md` склеивает документы в один markdown,
каждый под своим H1 (title из паспорта или имя файла).

Обратный путь один: ответы, конспекты и заметки возвращаются в корпус
через `inbox/` и `ingest-docs`, как любой входящий файл. MCP-серверов и
авто-синхронизации к NotebookLM в ядре нет — они держатся на cookies и
недокументированных API и ломаются тихо, унося с собой доверие к
содержимому ноутбука.

## Ограничения — честно

- `mermaid`-блоки в PDF не рендерятся: ядро не возит рендерер.
  Диаграмма нужна в сдаче → положи рядом её PNG (`![[диаграмма.png]]`),
  экспортёр встроит; или сдавай `.html`, если у получателя есть браузер.
- Пакет из нескольких документов — прогони экспортёр по каждому и собери
  манифест сдачи (что, кому, дата, версии) в `stages/NNN-delivery/`:
  сдача пакета это `stage`.
